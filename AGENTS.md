# AGENTS.md

## Default Architecture: Clean Architecture

All code must follow Clean Architecture — dependencies point inward. Cross-boundary data uses DTOs, not entities. See `.opencode/rules/clean-architecture.md` for the full rule set.

Layers: Entities → Use Cases → Interface Adapters → Frameworks & Drivers

## Security by Design

Security is a first-class architectural constraint, not an afterthought. Apply:
- **Validate all inputs** at system boundaries — reject early, reject explicitly
- **Principle of least privilege** — grant minimal access for each operation
- **Fail securely** — default-denied access, explicit allow-lists
- **Defense in depth** — multiple independent checks, not a single gate
- **No secrets in code** — use env vars or config, never literals
- **Immutable domain entities** where possible — reduce attack surface from mutation

That job runs a **second** audit beside it since 2026-09-04 — `tools/supply-chain/audit-containers.sh`, which holds the repository's three digest-pinned containers against `tools/supply-chain/expected-containers.json` ([ADR-064](docs/adr/ADR-064-pinned-container-audit-coverage.md)) — so do not describe `tools/supply-chain/` as covering npm plugins only. Both steps carry `if: always()`, so a container finding cannot hide plugin drift or the reverse. Run it *before* changing a pin and update the baseline in the same commit — never to turn a red job green. Only three of the seven carry provenance attestations; `vibeguard`, `scheduler`, `goal-plugin` and `smart-title` do not, which is less to verify against rather than evidence of a problem (SETUP.md holds the figures and the accepted residual). **High and critical advisories are gated against a second file, `tools/supply-chain/accepted-advisories.json`** — an allowlist of advisory IDs, each carrying the traced reason it is unreachable. It fails in both directions: an unlisted high fails the job, and so does a listed advisory that is *no longer reported*, which means delete the entry rather than leave it. Never add an entry to turn a red job green, and re-verify reachability whenever one of the pins involved moves. Smart-title is also the one hole in the exact-pinning guarantee — its auth provider can `bun add …@latest` an undeclared package at runtime, which the audit script cannot see (Blueprint §12.9). Graphify (knowledge graph) is not an npm plugin entry — the CLI is pinned repo-locally in `tools/graphify/` and placed on `PATH` by `.envrc`, and `.opencode/plugins/graphify.js` is a directory-loaded local plugin. Graphify's own minimum is Node ≥ 20, but do not read that as the version to install: the repository floor is **22.12**, set by the front end (`ui/package.json` `engines.node >= 22.12`, itself set by Vite 7's `^20.19.0 || >=22.12.0`) and built on 22 in CI (`.github/workflows/ci.yml`, where `node-version: 22` resolves to the latest 22.x and so clears the patch floor). The patch level is load-bearing rather than pedantic — Node 22.0–22.11 satisfies a bare ">= 22" while violating Vite's own range. Do not expect `npm install` to stop you, though: `engine-strict` is unset and there is no `.npmrc` at the repository root or in `ui/`, so npm prints an `EBADENGINE` **warning** and installs anyway, leaving the mismatch to surface later as a confusing Vite failure instead of at install time. Node 20 reached end-of-life on 2026-04-30. See Blueprint §5.
- **Autonomous completion is gated, not self-declared.** Under `/goal` the Tech Lead runs autonomously but cannot declare a story done on its own: it must collect explicit approvals from all seven of @tester-unit-and-quality, @tester-api, @security-auditor, @code-reviewer, @architecture-guardian, @sonarqube-expert and @dependency-vulnerability, and `./mvnw verify` counts as one piece of evidence rather than the gate. The goal-plugin's `completionAudit` then spawns an independent read-only auditor that must approve the evidence, and rejection pauses the goal instead of archiving it. Two known limitations: the auditor inherits `MODEL_A` — the *same model ID* as `tech-lead`, not merely the same family, so by Blueprint §3.1's definitions that audit is neither family- nor model-independent — and cannot be repinned, and it has no `bash`/`task` access so it inspects evidence rather than re-running checks. **Never create `.opencode/agents/goal-verify.md`** — it makes the plugin throw at startup (still true on the current `0.8.1` pin: the guard is `src/native-agent-config.js:27-31`, unmoved across four releases). One further behaviour to expect while those seven gates run: `noContinueWhileChildrenActive` is **on**, so auto-continue is deferred while any child session is live rather than prompting the Tech Lead over work a subagent is already doing. A `/goal status` reading `deferred` therefore means *waiting on a subagent*, not a hung loop — do not nudge it. It fails open on hosts that cannot report children, so a stalled goal is never explained by this alone. It has also never been *observed* firing: deferral is only recorded when an auto-continue attempt is suppressed, and auto-continue only fires once the session goes idle, so a turn that dispatches a subagent and then inspects `get_goal_history` cannot see it — treat the flag as configured-but-untested and revert it first if `/goal` misbehaves (Blueprint §12.8). Full rationale in Blueprint §12.8.
- **Model tiers are `MODEL_A`–`MODEL_G`, and there are only six distinct models.** `.opencode/opencode.json` pins every agent through one of seven environment variables (all seven are asserted by `.envrc`), but **`MODEL_E` is deliberately the same model ID as `MODEL_C`** — `ui-builder` shares the coder tier rather than having one of its own. The separate variable exists so the front-end can be repointed later without disturbing the back-end agents; do not assume seven distinct tiers exist, and do not "fix" the duplication. `MODEL_F` was added on 2026-08-21 by [ADR-046](docs/adr/ADR-046-gate-model-capability-floor.md) to hold the two review gates that audit `MODEL_A`'s own output — `architecture-guardian` and `security-auditor` — and since 2026-09-02 it holds **four** agents, because [ADR-061](docs/adr/ADR-061-two-new-dod-gates-sonar-ratchet-and-cve.md) added `sonarqube-expert` and `dependency-vulnerability` to it. Do not describe it as the two-gate tier. Note it is the `MODEL_C`/`MODEL_E` precedent inverted, and deliberately so: there, one model behind two variables so each can be repointed independently; here, several agents behind one variable because their requirements are identical and every extra variable multiplies drift across the tier tables. The two 2026-09-02 additions landed there rather than on a new `MODEL_H` for the same reason, and they were only *eligible* for it because neither authors anything — the only `MODEL_F` author is `architecture-guardian`, and neither new gate reviews architecture documentation, so the tier gained two gates without gaining an overlap. `MODEL_G` was added on 2026-08-24 by [ADR-059](docs/adr/ADR-059-code-review-gate-on-its-own-model-tier.md) and holds `code-reviewer` alone, pinned to `amazon-bedrock/zai.glm-5` — a sixth model family. It is the `MODEL_F` case again for a single agent rather than two, and it exists because the shortage was arithmetic: with five distinct models spread over six variables, some gate necessarily shared a tier with some agent that authored what it reviews, so no rearrangement of the existing six could have closed the last exception. The `agent` block is grouped by tier, so move an agent between groups rather than editing its value in place.
- **A review gate must not share weights with an agent that writes production code — and since 2026-08-24 that holds with zero exceptions for production code, infrastructure and test code.** It binds *delegated* authoring, and `MODEL_A` writes Java, which is why the rule had to be enforced rather than asserted: until 2026-08-24 test code shared `MODEL_B` with `@code-reviewer`, which reviews it, so identical weights judged identical weights. [ADR-059](docs/adr/ADR-059-code-review-gate-on-its-own-model-tier.md) closed that by moving `@code-reviewer` alone to `MODEL_G` (`amazon-bedrock/zai.glm-5`, a sixth family), and `SeparationInvariantTest` now fails `./mvnw verify` if any gate is repinned onto a tier that authored an artefact class it reviews. **Zero exceptions for those three artefact classes is not the same as unconditional, and the qualifier may never be dropped:** `@security-auditor` still shares `MODEL_F` with `@architecture-guardian`, which *authors* ADRs and C4 models, so architecture documentation is still reviewed by a tier-mate at one model identifier — neither model- nor family-independent. That surviving overlap is carried as the single declared, justified and self-retiring allow-list entry in that test, so it cannot decay into silence. There were **two** until 2026-08-21 — production code the primary agent or `@tech-lead` authors itself also shared `MODEL_A` with two of the five gates — and [ADR-046](docs/adr/ADR-046-gate-model-capability-floor.md) closed that one by moving `architecture-guardian` and `security-auditor` to `MODEL_F`, so `MODEL_A`-authored production code is now reviewed family-independently by both. Do not cite two exceptions after that date, and do not cite one after 2026-08-24. Both, and the dates each was closed, are recorded in [ADR-022](docs/adr/ADR-022-agent-model-tier-governance.md), which also defines the two degrees of independence — *family*-independent versus the weaker *model*-independent — that any claim about review separation must be stated in. Cite this rule with its architecture-documentation qualifier and use `/trace` to find which case a story is in. Both `tester-unit-and-quality` and `tester-api` were moved from `MODEL_C` to `MODEL_B` for this reason: `MODEL_A` writes Java, `MODEL_C` writes migrations and CI/IaC, `MODEL_E` writes the front-end, and `MODEL_B` authors no production code at all. On `MODEL_C` `tester-unit-and-quality` needed three dispatches to return a verdict and once recommended merging a red build; `tester-api` then failed the same way on the same tier under EOP-26 — four dispatches, `VERDICT: APPROVE` every time but with none of the contracted evidence, once substituting headings of its own for the brief's required outputs and once claiming its evidence had been "compiled in a markdown document" it was never permitted to write. **A DoD gate agent must therefore satisfy the ADR-046 capability floor: reasoning-capable, structured tool calls, at least 40,000 max output tokens and 128,000 context, family-independent of every tier that authored the artefact under review, and a passed two-stage probe recorded in Blueprint §3.4.1 — a gate pin with no recorded passing verdict is non-compliant.** `MODEL_C`/`MODEL_E` remain ineligible, but as a *consequence* of that floor (neither is reasoning-capable) rather than by name; `MODEL_A`, `MODEL_B`, `MODEL_F` and `MODEL_G` satisfy it today, and the seven gates sit on `MODEL_B`, `MODEL_F` and `MODEL_G`. The other half of that fix is in the agent definitions themselves: all seven gate agents now carry a **Sign-off Contract** (a mandatory final `VERDICT: APPROVE`/`VERDICT: REJECT` line, severity-tagged findings with `file:line`, actual command output rather than intent, answer the brief's enumerated outputs rather than a structure of your own, the reply is the only deliverable so never claim a file was written, never end with a question, never approve a red build) and a **read-only-while-reviewing** rule. Both were previously enforced only by whatever the dispatching prompt happened to say, which is why they were skipped. The `file:line` clause has one measured exception, and it is a bound on the evidence rather than a relaxation: `@sonarqube-expert` adjudicates an artefact whose issue fingerprint carries a *content* hash and no line number at all, so it cites quality, rule key and path exactly as the ratchet prints them and is forbidden from supplying a line or a rule meaning it cannot quote from a file in the repository — a rule added after a probe watched `MODEL_F` invent two rule titles and dismiss two genuine findings as scanner false positives (ADR-061). `performance-engineer` remains on `MODEL_C` and carries no Sign-off Contract — it is not one of the seven gates, and dispatching it as one is unsupported.
- **Scratch work goes in `.tmp/` at the repository root — never `/tmp`, never the parent directory, and since 2026-09-05 the shell will refuse rather than remind you.** `.tmp/` is gitignored and *inside* the worktree, which is the whole point. **Do not repeat the justification this bullet carried until 2026-09-05 — that an unconfigured `external_directory` permission makes every touch of `/tmp` "block on a prompt the human may not notice for minutes". It was measured false for the way scratch files are actually created.** `external_directory` gates the *file* tools; it does not gate `bash` at all, so a heredoc or a `>` redirect into `/tmp` from a shell command never consulted it and was silently permitted by `permission.bash`'s `"*": "allow"` wildcard. The rule was prose with no enforcement behind it, and on 2026-09-05 an agent that had read this file wrote nine scratch files to `/tmp` in one day. It is now enforced by six `deny` entries at the **end** of the `permission.bash` map — `*/tmp/*`, `*/tmp`, `*/tmp *`, `*/var/folders/*`, `*$TMPDIR*`, `*mktemp*` — and the deny is *self-teaching*, because the refusal names the rule to the agent at the moment it reaches for the wrong directory, which prose in this file demonstrably is not. Four things follow. **`.tmp/` is provably unaffected**, because `*/tmp/*` compiles to an anchored regex needing the literal substring `/tmp/` and a worktree path offers `/.tmp/` — verified by a positive-control probe, not by reading the glob. **This overrules your bash tool briefing**, which recommends `/var/folders/vv/…/T/opencode` as "pre-approved for external directory access": that path is now denied outright, and the briefing's claim was already falsified once on 2026-08-20 (Blueprint §7.8). **A deny on a command *pattern* is a speed bump, not a boundary** — it matches command text, so it cannot see inside a script it invokes, and `bash -c '…'` is a single node — so keep writing to `.tmp/` because it is correct, not because you would otherwise be stopped. And **the map is read at process start**, so editing it does not disarm the session you edit it from; verify a change behaviourally in a fresh `opencode run`, never by inspection. The observed evidence is quoted in Blueprint §7.9, and `OpencodeTmpDenyRulesTest` fails `./mvnw verify` if any of the six entries is removed. One grant of the opposite sign also exists, for a different mechanism: the `bash` ruleset carries `"rm *": "ask"`, which fires on scratch cleanup wherever the file lives, so `.opencode/opencode.json` allows `rm` for `.tmp` and `.tmp/*` specifically. Those entries sit *after* `"rm *"` deliberately — opencode evaluates the **last** matching bash rule, so moving them above it silently reinstates the prompt — and each anchors the path immediately after the flags rather than using a leading wildcard, so a command cannot smuggle an unrelated path into an allowed `rm`. **Prefer `git worktree add .tmp/scratch HEAD` over copying** — the tree is 1.9 GB (600M `tools/graphify/node_modules`, 174M `target`, 127M `ui/node_modules`, 108M tracked PDFs under `docs/`) but only 634 tracked files, so `cp -r .` is three orders of magnitude more work than a checkout; copy results back with `git diff` + `git apply`, and clean up with `git worktree remove .tmp/scratch`. Two hard constraints. It **must** stay at the root: `DeckArithmeticClaimsTest` recursively `Files.walk`s `docs/` and `src/`, so a scratch copy under either turns `./mvnw verify` red on duplicated prose (Checkstyle, SpotBugs, Liquibase's `<includeAll>` and `ui/tsconfig.json`'s `include` are all scoped and unaffected). And never launch `opencode` from inside it — same nested-config hazard as `.opencode/`, described below. Unverified caveat: whether `graphify update .` honours `.gitignore` is not established (`graphify update --help` exposes no `--exclude`), so after a large scratch session check with `graphify` for duplicated nodes rather than assuming exclusion. Rationale in Blueprint §7.9.

## OpenCode Agent System

This project uses a multi-agent team defined in `.opencode/agents/`. Thirteen delivery agents:
- `@product-owner` — requirements discovery and backlog management
- `@tech-lead` — engineering orchestration and enforcement
- `@architecture-guardian` — C4 models and ADRs
- `@devops-engineer` — infrastructure and CI/CD
- `@db-designer` — database schemas and migrations
- `@ui-builder` — accessible front-end components
- `@tester-unit-and-quality` — unit test automation
- `@tester-api` — API integration tests
- `@security-auditor` — security and vulnerability audits
- `@code-reviewer` — static code review and SOLID compliance
- `@sonarqube-expert` — adjudicates **both** SonarQube issue ratchets over production code against their committed baselines: the Java one over `src/main/java`, and since 2026-09-03 ([ADR-063](docs/adr/ADR-063-sonarqube-frontend-project.md)) a second, independent one over `ui/src`
- `@dependency-vulnerability` — adjudicates the Trivy CVE scan over the shipped dependency trees
- `@performance-engineer` — benchmarks and load testing

Plus four advisory experts, with no Jira or GitHub access — invoke them by name for a second opinion:
- `@expert-uncle-bod` — software craftsmanship, SOLID, Clean Architecture
- `@expert-dave-farley` — continuous delivery, TDD, fast feedback
- `@expert-kent-beck` — TDD, XP, incremental refactoring
- `@expert-alex-xu` — ultra-high-scale distributed systems and storage

All agents are `mode: subagent` except `tech-lead` and `product-owner`,
which are `mode: all` — they are selectable in the **Tab** primary-agent cycle *and* still
dispatchable via `@` / the Task tool.

**Tab, not `@`, for a conversation.** Tab replaces the agent you are talking to while keeping the
whole message history, so the new agent sees everything that came before. `@agent-name` dispatches
a *one-shot subagent* in a child session: one prompt in, one message out, no way for it to ask you
a question and hear the answer. The Product Owner's discovery interview and the Tech Lead's
orchestration of a whole story therefore only work via **Tab**; `@` is for bounded, self-contained
work such as a review or an audit. `mode: all` rather than `primary` is deliberate for both, so the
Tech Lead can still dispatch the Product Owner for stage 0 of its own pipeline.

Intended flow for a new piece of work: **Tab to Product Owner** and be interviewed until
requirements are frozen and stories are filed → **Tab to Tech Lead**, which sees the whole
interview, to run delivery → **Tab back to `build`** for tooling, configuration and meta-work.

**Always launch `opencode` from the repository root.** OpenCode scans `.opencode/agents/`
recursively for `*.md`, but bootstraps its plugins and goal state into `$PWD/.opencode/`. Starting
OpenCode from inside `.opencode/` makes those two paths collide, so ~30 dependency
`README.md`/`CHANGELOG.md` files get registered as phantom agents and pollute the Tab cycle.

Two guards enforce this, because documentation alone did not prevent a recurrence:

1. **`opencode()` shell wrapper** (in `~/.zshrc`, per-developer, not in the repo) resolves
   `git rev-parse --show-toplevel` and launches OpenCode from there via a subshell `cd`, so the
   calling shell's working directory is unchanged. Outside a git repo it passes through untouched.
   Note the `opencode [project]` positional argument only works for the default TUI command, not
   for subcommands like `run`, which is why the wrapper uses `cd`.
2. **`.opencode/agents/.opencode` sentinel** — a committed *regular file*, not a directory. It
   makes the nested tree physically impossible to create: launching from the wrong directory now
   fails fast with `BadResource: FileSystem.readFile (.../.opencode/agents/.opencode/opencode.json)`
   instead of silently registering phantoms. Do not delete it and do not turn it into a directory.

The `.opencode/**/.opencode/` rule in `.gitignore` only keeps `git status` clean — it does not stop
phantom registration, and its trailing slash means it does not match the sentinel file.
