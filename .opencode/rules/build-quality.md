- Build MUST pass before any PR merge (`mvn verify` in CI)
- Code style enforced by `checkstyle` against the repo's own `checkstyle.xml` (4-space indent, 140-char line limit — NOT Google Java Style) — violations fail the build. **Since EOP-120 it also enforces Javadoc *presence*, and that is now the bigger day-to-day constraint:** `MissingJavadocType` and `MissingJavadocMethod` at `scope=public` require a comment on every public type, method and constructor in `src/main/java`, and `JavadocMethod` requires every `@param` and every `@return` (`allowMissingParamTags` and `allowMissingReturnTag` are both `false`, and `minLineCount` is `-1` so a one-line public getter is not exempt). This is deliberately one half of a two-tool split and the half that is easiest to weaken by accident — do not relax `minLineCount` or any `allowMissing*` to silence a complaint about a getter. Changing them means amending ADR-006, because Checkstyle owning *missing* is what lets the Javadoc plugin run with `-missing` off
- Static analysis via `spotbugs` — high/medium severity findings fail the build
- Code coverage via `jacoco` — minimum 80% instruction and 70% branch coverage, both evaluated over the whole bundle (`pom.xml:169`) with no exclusions and no per-class rule; the branch limit was restored by EOP-15 slice B once the domain had branches to measure — see ADR-006 as amended by ADR-031
- `maven-enforcer-plugin` enforces: JDK >= 21, dependency convergence (no version conflicts), no banned dependencies
- **Javadoc is a build gate, and it is enforced by two tools rather than one.** `maven-javadoc-plugin` 3.11.2 runs `javadoc-no-fork` in the `verify` phase with `failOnError`, `failOnWarnings`, `show=public` and **`doclint=all,-missing`**, so a broken `{@link}`, a malformed tag or bad HTML in `src/main/java` fails the build. The `-missing` is load-bearing, not a shortcut: doclint's `missing` group ignores the `-public` flag and would demand a comment on every *private* field (~50 across the domain exception classes), and `doclint=all/protected` cannot be used at all — javadoc rejects access qualifiers on `-Xdoclint` outright. So the plugin owns **malformed** and Checkstyle owns **missing** (see the Checkstyle bullet above); never "simplify" this to `doclint=all`. The version is pinned exactly and is **not** covered by `tools/supply-chain/`, which audits the seven OpenCode npm plugins and, since 2026-09-04, the six digest-pinned containers ([ADR-064](../../docs/adr/ADR-064-pinned-container-audit-coverage.md)) and, since 2026-09-07, every `uses:` reference in `.github/workflows/` ([ADR-073](../../docs/adr/ADR-073-supply-chain-coverage-for-actions-and-browsers.md)) — the whole Maven layer is still uncovered, and this plugin is one of the seven declared Maven plugins (`spring-boot`, `failsafe`, `checkstyle`, `javadoc`, `spotbugs`, `jacoco`, `enforcer`), so do not add it alone to that baseline — extending coverage to the Maven layer means the fifteen bound entries plus the wrapper. Two corrections to make before citing that set. First, **liquibase is not one of them**, it executes during tests as an application dependency and no `liquibase-maven-plugin` is declared — though the Boot parent *does* carry one in the effective `pluginManagement`, as a bare entry with coordinates and a version but no `<executions>` and no `<configuration>`, so nothing binds it to a phase and it never runs. That version is deliberately not quoted here: unlike the plugin versions this file does name, it is not ours to pin — it comes from the parent's own `liquibase.version` property, so a Boot bump moves it with no signal to this file and no test to catch the drift. Read it off `./mvnw help:effective-pom` when you need it, and do not helpfully restore a literal. Second, only **five** of the seven carry a version in `pom.xml`: `spring-boot-maven-plugin` and `maven-failsafe-plugin` carry none, the former taking 4.1.0 from the Boot parent, so never write that all seven are pinned in this file. And `maven-enforcer-plugin` was **not** floating before EOP-120 — it carried no version of ours but was parent-managed at 3.6.3 by `spring-boot-dependencies:4.1.0`, hence already exact and reproducible; the pin added via `maven-enforcer-plugin.version` buys deliberate control rather than closing a hole, and its flip side is that a future Boot bump to enforcer no longer reaches us, exactly as already applies to `maven-javadoc-plugin` (Boot owns 3.12.0, we hold 3.11.2). The seven declarations are also not the layer: the effective `build/plugins` binds **fifteen** entries including `maven-compiler-plugin` and `maven-surefire-plugin`, and the effective `pluginManagement` carries **thirty-one**, so bumping the parent coordinates moves about thirty plugin versions in one line — that, not the seven, is the real uncovered surface. "No **enforced** verification" is the precise phrasing at this layer: Maven compares a `.sha1` and warns, never fails, there is no `maven.config` and so no `--strict-checksums`, and `maven-wrapper.properties` carries no `distributionSha256Sum`. Three surprising directions. **A comment-only edit to a `.java` file can now turn `./mvnw verify` red**, which extends the blast radius of the prose gates below into source Javadoc. A warm `target/` may log `Skipping javadoc generation, everything is up to date.`, and the goal's mere presence in a log is **not** proof it re-analysed your edit — the staleness record holds 117 paths of which 92 are `.jar` and **zero** are `.java`, because the plugin's `StaleHelper.walk` uses a non-recursive `Files.newDirectoryStream`, so a Javadoc-only change need not invalidate it; CI is always the cold path (fresh runner, no `target/`) so every merge is gated on a full analysis, but locally run `./mvnw clean verify` before pushing if you only touched comments. And `debug=true` in the plugin configuration is **not** leftover scaffolding, though its justification is narrower than it first appeared: it retains `javadoc.sh`, `options` and `packages` instead of deleting them, which makes the flags that actually reached the tool auditable and a failure diagnosable. Keep it for that. Do **not** repeat the retracted claim that removing it reinstates a failure — a warm `./mvnw verify` was once seen failing with `Unable to compute stale date: target/reports/apidocs/options` on an entirely correct tree, but with `debug` removed that could not be reproduced in five controlled attempts, so the failure stands as observed and unexplained and `clean` is the workaround if you meet it. The check *both states and reads* `@`-prefixed argument files, and never `stat`s them — the record *both* names `@options` and `@packages` as bare argument lines *and* carries their expanded contents, and `options` is rewritten at the start of every invocation. See ADR-006 as amended 2026-08-20 (EOP-120)
- **Prose is a build gate too.** Documentation-integrity tests in `src/test/java/org/maglez/eop/docs/` run as part of the same `verify` phase and read repository files as text: `TrickPlayExceptionOriginTest` (EOP-14) pins an ADR-023 paragraph to the adapter, `AdrIndexConsistencyTest` (EOP-32) holds `docs/adr/README.md` against every ADR's status line, `DeckArithmeticClaimsTest` (EOP-93) checks deck-arithmetic claims across **all** of `docs/**/*.md` and `src/**/*.java`, `EnumMirrorParityTest` (EOP-105) holds four mirrored enums (`PlayerRole`, `SessionStatus`, `ConnectionStatus`, `StrideCategory`) in three-way agreement across the Java enum, the `enum:` lists in `docs/api/openapi.yml` and the `as const` arrays in `ui/src/api.ts`, `MermaidSequenceTextTest` (EOP-000) forbids `;` and `#` in every label of every Mermaid `sequenceDiagram` fence under `docs/**/*.md`, `OpenApiContractDriftTest` (EOP-095) compares the generated springdoc document against the hand-authored OpenAPI contract on path+method and response-status axes, `JoinCodeSpaceClaimsTest` (EOP-56) holds the join-code alphabet and space arithmetic, `SourceCitationAnchorTest` (EOP-130) checks that every `Foo.java:123` citation in `docs/**/*.md` names a file that exists and lines that exist, and that any citation carrying an explicit `` (anchor: `token`) `` really does contain that token in the range it names, `K6ThresholdCouplingTest` (EOP-158) holds the k6 CI threshold count in `.github/workflows/ci.yml` against `test/k6/config/options-ci.js`, `K6ScenarioWiringTest` (EOP-204) holds every scenario file in `test/k6/` against an actual `run_canary` invocation in the workflow, and `K6LatencyCheckTest` (EOP-206) fails if a k6 `check()` predicate reads the `timings` object — the exact shape EOP-157 deleted that read as a latency gate while gating nothing. **What it does not prove:** the remaining predicates are meaningful (that is `K6ScenarioWiringTest`'s bound), a latency assertion written without `timings` (such as `Date.now()` arithmetic) is recognised, or that the sanitiser correctly handles a regex literal containing a quote or a template literal with `${...}` interpolation — all three stay reviewer-enforced. **`SourceCitationAnchorTest` is the one gate whose scope is opt-in rather than universal, and the distinction is the whole design:** the two structural checks bind all ~171 named citations, but only an *anchored* citation is verified to point at the right code, because inferring the anchor was measured and rejected — 36 of 67 inferred anchors were false positives, since ~58 citations deliberately target javadoc and drift-onto-javadoc was EOP-49's own failure mode, making the two indistinguishable. Opting in also buys something structural: a citation quoted inside an immutable dated amendment block stays truthful as history instead of being rewritten to satisfy a checker. Add the anchor whenever you write a citation you want protected — an unanchored one is checked only for resolvability and range — and note the marker must sit *immediately* after the citation in one of the two supported forms, because a ninth test fails the build on any `anchor:` marker the parser did not bind rather than letting it read as enforced while doing nothing. `DbSchemaDiagramTest` (EOP-167) holds the `erDiagram` in `docs/architecture/db-schema.md` against the Liquibase changelogs in both directions — every `createTable` table name must have an entity block, and every entity block must name a table some changelog creates — and adds three structural checks: every entity block closes, no relationship endpoint names an undeclared entity, and a `MINIMUM_ENTITIES` floor so no rule can pass over an empty list. Like `MermaidSequenceTextTest` it is structural rather than a phrase list, and it is bounded in three ways worth knowing before trusting it: it is **not** a Mermaid syntax check, so a malformed column line or an invalid cardinality token still renders broken and still passes; column types, nullability and the `ON DELETE` annotations are reviewer-enforced; and because it extracts `createTable` only, it would keep accepting a stale entity after the first genuine `dropTable` — at which point subtract dropped names read outside `<rollback>` blocks. `PlaywrightImagePinTest` (EOP-236) holds the pinned `mcr.microsoft.com/playwright:v<MAJOR.MINOR.PATCH>-noble@sha256:<64 hex>` reference in `.github/workflows/ci.yml` and the `tag` recorded for that image in `tools/supply-chain/expected-containers.json` against the `@playwright/test` spec in `e2e/package.json` and the version resolved for it in `e2e/package-lock.json` — all four must name the same release, because a container whose browsers were built for a different Playwright version makes the suite refuse to start with a message about a missing browser executable rather than a version mismatch. It is the same *shape* as the two k6 gates rather than a prose check: it reads a workflow against a manifest. Three bounds worth knowing: it fails on an unpinned mention and on a range operator, so dropping the digest or restoring a caret is caught, but it **cannot** prove the digest actually corresponds to the tag — that needs the registry and is `tools/supply-chain/audit-containers.sh`'s job, which is not part of `./mvnw verify` — and it says nothing about whether the pinned release is current. So editing a Markdown file anywhere under `docs/` can turn the build red — and so can editing `docs/api/openapi.yml` or `ui/src/api.ts`, which is the surprising direction: a front-end enum rename that passes `npm run verify` in `ui/` fails `./mvnw verify`. Three consequences worth internalising: their matchers are phrase lists rather than semantic analysis, so **a green build is not proof that documentation is correct** — it only proves the specific phrasings that have gone stale here before are absent; their *coverage* is likewise a hand-written list, so nothing detects a fifth mirrored enum added to `ui/src/api.ts` without a row in `EnumMirrorParityTest.mirrors()` — and that is not hypothetical, because `StrideCategory` was exactly such an unregistered mirror, found by a review agent rather than by the build, and registered only during EOP-105's own gate round; a further consequence of the same shape is that `typeScriptArrayValues` recognises only the `export const NAME = [...] as const;` idiom, so registering a mirror written as a bare union means rewriting the declaration first; and if one of these guards ever becomes unfireable (invariant B is meaningless once no supported table size divides the deck evenly), **delete it rather than leave it passing**, per the branch-coverage lesson in ADR-006. `MermaidSequenceTextTest` sits differently to the other four on the first of those consequences and squarely inside the third: it is structural rather than a phrase list, so it holds for diagrams nobody has written yet — but it proves only that two characters are absent, never that a diagram renders or says anything true, and its own coverage is the hand-written `MINIMUM_SEQUENCE_DIAGRAMS` floor that stops it silently matching nothing. See ADR-006 as amended 2026-08-18 (EOP-93), 2026-08-19 (EOP-105) and 2026-08-20 (EOP-000 and EOP-120)
- **SonarQube issue counts are ratcheted, and the ratchet is not part of `./mvnw verify`.** Three integers — Reliability, Maintainability and Security — are held at a ceiling in `tools/sonar/sonar-baseline.json`, and the `sonar-ratchet` CI job fails if any of them rises by even one. **Those three integers cover production code only — `src/main/java`, which is SonarQube's MAIN scope — and have done since 2026-09-02 ([ADR-060](../../docs/adr/ADR-060-sonarqube-issue-ratchet.md) as amended).** Two things follow that are easy to get wrong in both directions. They are **not** the numbers the SonarQube project overview page shows, so reading `MAINTAINABILITY 31` as the project's total is wrong by an order of magnitude; the whole-tree figure is recorded beside them in `tools/sonar/sonar-report.json` under `scope.ALL`, and `scope.MAIN` plus `scope.TEST` reconciles with it per quality, which is what makes the narrowing auditable from the file rather than asserted here. And test code is **still analysed and still hashed** — only the gate narrowed, not the analysis — so its findings are measured and recorded under `scope.TEST` while never gating, and a green `sonar-ratchet` says nothing whatever about the 36,965 lines under `src/test/java`. The reason for narrowing was **not** coverage, and must never be restated as though it were: SonarQube already classifies `src/test/java` under `sonar.tests`, so coverage read 95.1% with test code fully in scope before the change and reads 95.1% after it. The reason was that 211 of 243 findings sat in test code against a ceiling with no headroom, so a routine new test file reddened a gate that had nothing to say about the product. It is a comparison of two committed JSON files with no server and no LLM in the path, deliberately so (ADR-060), and it lives in its own job because the SonarQube scanner is *not* declared in `pom.xml`: `./mvnw verify` can be green while the ratchet is red. Four consequences for anyone writing code here. **Write to the ceiling, not to the gate** — a new issue of any of the three qualities fails the job whatever its severity, so treat "would SonarQube flag this?" as a question with the same standing as Checkstyle and SpotBugs, and note there is no tolerance and no aggregate: the counts are compared per quality. **Prefer the fix, always.** Raising a ceiling is always available and almost never right; a raise must land in the same commit as the code, name the rule that fired, and argue why living with the finding beats fixing it — a raise with no argument is one a reviewer must reject. **A code change means a rescan**, because the report carries a `sourceHash` over `pom.xml` and every `.java` file under `src/main/java` and `src/test/java`; a stale report fails the job before any count is compared, and the fix is `tools/sonar/scan.sh` with the local container up, committing both JSONs. A change touching only documentation, workflows or `ui/` leaves that hash intact and needs no rescan. And **`--tighten` is local-only** — `scan.sh` passes it to lower the ceiling when a scan finds fewer issues, and nothing in CI or in a review may pass it. Coverage is not gated here at all; JaCoCo owns it at the limits above
- **Since 2026-09-03 there are two such ratchets, not one, and everything above describes only the Java half.** [ADR-063](../../docs/adr/ADR-063-sonarqube-frontend-project.md) added a second SonarQube project, `eop-threat-modeling-ui`, over `ui/src`, with its own three integers in `tools/sonar/sonar-ui-baseline.json`, its own evidence in `sonar-ui-report.json`, its own entry point `tools/sonar/ratchet-ui.sh` and its own CI job `sonar-ratchet-ui`. Every caveat in the bullet above applies to it verbatim, so treat the pair as one mechanism instantiated twice rather than as two things to learn. **Two projects rather than one polyglot project is the load-bearing decision**: a single set of three integers would let a new front-end finding be paid for out of Java headroom, and the number would keep moving truthfully while meaning nothing about either population. Four consequences. The two jobs carry **no `needs:`** and fail independently, so a red front-end ratchet never hides a red Java one. The two freshness tokens are **deliberately disjoint** — the Java hash covers `pom.xml` and every `.java` file under `src/main/java` and `src/test/java`, while the front-end hash covers `ui/package.json`, `ui/tsconfig.json`, `ui/vite.config.ts` and every `.ts`/`.tsx` under `ui/src` — so a Java-only change leaves the UI report fresh and a front-end-only change leaves the Java report fresh, and neither language's authors are asked to boot a container for the other's change. `ui/package-lock.json` is excluded from that hash on purpose, because the TypeScript sensor reads `tsconfig.json` and source rather than the lockfile, so including it would force a rescan on every `npm audit fix` for a change that provably cannot move a count. And the rescan command differs: `tools/sonar/scan.sh` for Java, `tools/sonar/scan-ui.sh` for the front end — the latter running the scanner as a **digest-pinned `sonarsource/sonar-scanner-cli` container** rather than a Maven plugin, since `ui/` has no `pom.xml`. Note the front-end scanner image is amd64-only and runs under emulation on Apple silicon, so that scan is slow; and moving its digest is both a supply-chain change and a baseline-invalidating one, because a scanner upgrade ships retuned rules. **Front-end coverage is measured and recorded but never gated** — `npm run coverage` in `ui/` writes `ui/coverage/lcov.info` via `@vitest/coverage-v8` and the figure lands in the report, but there is deliberately no `thresholds` block in `ui/vite.config.ts`, so unlike the Java side there is no JaCoCo-equivalent floor and a change halving front-end coverage passes provided it introduces no new issue. That asymmetry is intentional and argued in ADR-063; do not close it by adding a second number
- **Two of the seven Definition-of-Done gates read those two scanners, and both can reject your change.** `@sonarqube-expert` adjudicates the ratchet described above — most sharply whether a ceiling raise was actually argued — and `@dependency-vulnerability` adjudicates the Trivy CVE scan (`tools/supply-chain/scan-dependencies.sh`, gating on HIGH and CRITICAL only, per ADR-050). Neither is the enforcement: the `sonar-ratchet` and `dependency-cve` jobs already fail mechanically, and neither agent can edit a baseline, an allowlist, `pom.xml` or `ui/package-lock.json` to make a red gate green. What they add is the judgement a script cannot make, so a change that raises a ceiling or adds an allowlist entry needs the argument written down before it is dispatched, not after it is rejected ([ADR-061](../../docs/adr/ADR-061-two-new-dod-gates-sonar-ratchet-and-cve.md))
