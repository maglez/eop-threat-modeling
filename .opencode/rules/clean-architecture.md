- Hexagonal Architecture (ports & adapters): dependencies point inward — domain (`org.maglez.eop.domain`) and application core (`org.maglez.eop.application`) know nothing of adapters or frameworks; adapters (`org.maglez.eop.inbound.*`, `org.maglez.eop.outbound.*`) depend on ports (`org.maglez.eop.application.port.in` / `port.out`); `org.maglez.eop.config` is the composition root that wires adapters to ports
- Inbound ports (`application/port/in`, e.g. `PlayCardPort`) are implemented by application services (`application/service`, e.g. `PlayCardService`); driven adapters implement outbound ports (`application/port/out`, e.g. `SessionRepository`) — controllers and schedulers are driving adapters, persistence/security/web-outbound classes are driven adapters
- Cross-boundary data uses DTOs, not domain entities
- Core business logic has zero framework imports (no Spring, no Jakarta)
- Database and UI are details, not core architecture
- **The dependency rule binds Javadoc too, and there is exactly one way to satisfy it.** When an inner-layer type must *name* an outer-layer one in prose — a domain type mentioning a repository port, say — write `{@code Type#member}`. Never `{@link Type#member}`, which needs an outward `import` to resolve, and never a fully-qualified `{@link org.maglez.eop.application.port.out.Type#member}`, which resolves without an import but emits a navigable outward reference in the generated docs and reads to the next author as licence for the real import. This is not stylistic: `pom.xml`'s Javadoc gate runs `doclint=all,-missing`, whose `reference` group **fails the build** on an unresolvable `{@link}`, so the tempting fix for that error is the import that violates the first bullet. The pattern to copy is `GameSession.java`'s `complete()` naming `{@code SessionRepository#recordCompleted}`, which explains itself in place. See ADR-006 as amended 2026-08-20 (EOP-120)
